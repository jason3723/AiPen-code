**The Flash/Flicker Mechanism:**

When switching from maximized → normal (unmaximize):
1. Mask shows (opacity: 0 → 1, CSS transition 0.12s)
2. `win.unmaximize()` is called — the Tauri/WebView2 window physically shrinks
3. The OS window manager animates the window resize
4. During resize, the raw WebView2 content may briefly be visible behind the mask

**Key flash sources I can identify:**

### 1. **Mask rendering delay (timing gap)**
```
overlayVisible = true  →  await nextTick()  →  await rAF()
                                                  ↓
                                          [mask DOM inserted but
                                           not yet painted to screen]
                                                  ↓
                                          win.maximize() starts
```
Between `overlayVisible = true` and the actual paint of the mask to screen, there could be 1-2 frames where the mask exists in the DOM but hasn't been composited yet. The `rAF()` ensures the browser has had a chance to render, but **on WebView2, especially with `contain: layout style` on the editor, the compositor pipeline might be delayed**.

### 2. **WebView2 compositor window resize tearing**
When `win.maximize()` is called, this is a native OS window resize on the WebView2 host window. Windows compositor (DWM) handles the window resize animation. During this animation:
- The WebView2 content area is physically resized
- If the mask overlay is rendered by the same WebView2 compositor, the mask IS being resized along with everything else
- The mask may briefly show the underlying content because the compositor buffer during resize might be stale or contain intermediate states

**This is the most likely cause**: The mask is inside the WebView2 itself. When the native window resizes, WebView2 has to re-composite everything. Even though the mask is `position: fixed; inset: 0`, during the resize animation the compositor may:
- Show a frame where the mask hasn't been painted to the new size yet
- Or show a frame where the underlying content is visible because the mask layer is being recomposited
- The `background: #1e1f2b` fills the area, but during resize, the compositor's swap chain may briefly show old buffer contents

### 3. **The "dirty frame" after resize (the code already tries to solve this)**
After resize, if the mouse is not on the window, WebView2 compositor goes to sleep. The frame buffer contains whatever was last rendered during resize — possibly intermediate/broken layout. When the mouse moves in later, the first frame rendered is dirty. But this is the scenario the code already addresses with `flushCompositorFrame()`.

### 4. **Mask removal timing**
When `overlayVisible = false`, the `.overlay-fade-leave-active` transition takes 0.25s. During this fade-out:
- The underlying content is revealed
- If the underlying content wasn't fully re-laid-out yet (ProseMirror still finishing layout calculations), the revealed content might look broken for a frame

### 5. **CSS `contain: layout style` side effects**
The `.editor-contained` class uses `contain: layout style` to freeze ProseMirror layout during resize. When this is released (step 1 of flushCompositorFrame), ProseMirror triggers a massive re-layout. This happens INSIDE the same compositor that's rendering the mask. Even though the mask is above the editor in z-order, the layout work can cause jank in compositing — the compositor might skip frames or show partial updates.

### 6. **WebView2-specific: GPU process frame scheduling**
WebView2 on Windows uses a separate GPU process for compositing. When the window is rapidly resized:
- The renderer process (your JS/Vue) pushes frames to the GPU process via IPC
- The GPU process composites and presents to the window swap chain
- During window resize, the GPU process might present frames at the WRONG SIZE before receiving the updated frame at the new size
- Since the mask is rendered in the same WebView2, it's subject to the same IPC latency

### Root Cause Summary

The fundamental problem is that **the mask overlay lives inside the same WebView2 that's being resized**. When the native OS window resizes:

1. **Before the mask paints**: There's a 1-2 frame gap between `overlayVisible = true` + `rAF()` and the actual composited frame reaching the screen → content is visible → flash.

2. **During the resize animation**: DWM animates the window from old size to new size. WebView2 receives WM_SIZE messages asynchronously. During the animation frames, the compositor might present frames where the mask doesn't yet cover the new window bounds, or the mask itself is being resized and briefly shows through.

3. **After resize, before flushCompositorFrame**: The editor layout is still frozen (`contain: layout style`), ProseMirror hasn't recalculated. If any imperfect masking happens here (like the mask somehow exposing the underlying DOM through antialiasing, subpixel gaps, or scrollbar areas), the stale layout is visible.

4. **Mask removal reveals incomplete layout**: The `flushCompositorFrame()` runs and then the mask fades out over 0.25s. But the flush might not have fully completed in the actual frame presented to screen.

**The real smoking gun**: The only way to truly eliminate flash would be to have the mask rendered OUTSIDE the WebView2 content area — for example, as a native OS-level overlay (a borderless top-level window positioned over the WebView2 window), or by telling the OS to suppress window content during resize. Since Tauri's `maximize()`/`unmaximize()` causes the native window to animate, and the mask is in the same WebView2, you'll always have a timing race.

## 闪屏机理分析

### 核心矛盾

**遮罩层和编辑器内容运行在同一个 WebView2 渲染进程中。** 当操作系统原生窗口 resize 时，遮罩和它试图遮住的内容在同一个合成管线中，这就产生了多个时间窗口的泄漏。

### 五条闪屏路径

#### 1. 遮罩首帧延迟（Paint Latency Gap）

```
overlayVisible = true
    ↓
await nextTick()        ← DOM 已插入，但 GPU 纹理还没生成
    ↓
await rAF()             ← 浏览器排上渲染队列，但还没提交到 GPU
    ↓
win.maximize() 调用     ← 窗口开始变化！
```

`rAF()` 只保证 JS 端回调执行了，**不保证**：
- WebView2 渲染进程已经把该帧提交给 GPU 进程
- GPU 进程已经合成并推到 swap chain
- swap chain 已经 display

**结果**：`win.maximize()` 启动时，屏幕上可能还没有遮罩层，用户看到的是原内容"裸奔"缩放 → **第一闪**。

#### 2. DWM 窗口缩放动画期间的合成撕裂

Windows DWM 做窗口缩放时有平滑动画。动画进行中：

```
Frame N:   WebView2 收到 WM_SIZE → 内容区域 = 中间尺寸
Frame N+1: WebView2 渲染管线还在处理上一帧的尺寸
Frame N+2: WebView2 提交新帧，但遮罩层还没 cover 新尺寸的全部区域
```

WebView2 的 GPU 进程通过 IPC 接收渲染进程的帧。窗口尺寸变化 → GPU 进程可能先拿到新的窗口尺寸 → 还没来得及收到渲染进程的新帧 → **用旧尺寸的内容拉伸/压缩显示** → 遮罩可能出现黑边或露出底层内容 → **第二闪**。

#### 3. "脏帧缓存"问题（你已经在处理的）

鼠标不在窗口上时，WebView2 合成器进入休眠模式以减少功耗。窗口 resize 产生的大量中间帧（脏帧）残留在合成器缓存中。

当你 `flushCompositorFrame()` 后立即 `overlayVisible = false` 然后用户鼠标移入：
```
合成器醒来 → 先提交缓存中的最后一个"脏帧"（可能是半成品布局）
           → 下一帧才是 flushCompositorFrame 准备好的干净帧
           → 用户看到脏帧→干净帧 = 闪屏
```

#### 4. `contain: layout style` 释放时的重排风暴

```typescript
isResizing.value = false   // 移除 .editor-contained
```

`contain: layout style` 抑制了 ProseMirror 的 ResizeObserver 回调。一旦释放：
```
ResizeObserver 批量触发 → ProseMirror 重新计算所有 NodeView 尺寸
→ 大量的 layout + paint 操作在同一帧内挤兑 GPU 预算
→ 合成器可能 drop frame → 遮罩还在但是底下已经开始剧烈重排
→ 遮罩 fade out (0.25s) 过程中，如果重排还没完成，底层内容可见时是坏的
```

#### 5. 遮罩遮挡不完整（边角泄漏）

遮罩虽然是 `position: fixed; inset: 0`，但 WebView2 的渲染有几个死角：
- **滚动条区域**：如果编辑器内容有滚动条，`overlay` 元素的 `overflow: visible` 情况下，滚动条可能穿透遮罩显示
- **WebView2 非客户区**：窗口阴影、圆角等由 DWM 绘制，遮罩无法覆盖
- **GPU 合成层边界**：如果遮罩和内容不在同一个合成层（compositor layer），合成时可能有 1px 的亚像素间隙

### 根本原因：架构层面的时序竞态

```
时间线：
t0:  JS 设置 overlayVisible=true, 等待 nextTick+rAF
t1:  win.maximize()  ← 操作系统开始改变窗口
t2:  DWM 动画进行中，窗口尺寸在变化
t3:  WebView2 收到 WM_SIZE，通知渲染进程
t4:  渲染进程在新尺寸下重新布局 + 合成
t5:  GPU 进程提交新帧到 swap chain
t6:  DWM 显示新帧在屏幕上
```

问题在于 **t1 到 t5 之间，整个管线是异步的**，没有任何同步机制保证"遮罩画面已经到达屏幕"才"允许窗口开始缩放"。遮罩和内容在同一个合成管线中，窗口缩放动作本身就破坏了遮罩的遮挡能力。

### 你当前方案的改进空间

| 时间点 | 当前做法 | 问题 |
|---|---|---|
| mask 显示 → maximize | `nextTick + rAF` | 只保证 JS 端，不保证屏幕已呈现 |
| maximize 后 | `sleep(400)` | 硬等，窗口动画时间不可控 |
| flush 后 → mask 隐藏 | 立即 `overlayVisible=false` | mask 消失时底层可能还在重排 |

### 根治方向（按效果排序）

1. **原生遮罩层**（最佳）：在 Rust 侧创建一个 `always_on_top` + 无边框 + 纯色背景的辅助窗口，在 resize 前后覆盖 WebView2 窗口。它独立于 WebView 渲染管线，不受 resize 影响。

2. **DWMWA 禁用窗口内容动画**：通过 Windows API `DwmSetWindowAttribute` 设置 `DWMWA_TRANSITIONS_FORCEDISABLED`，抑制 DWM 的缩放动画 → 窗口瞬间到位 → 遮罩只要在前后各一帧有效即可。

3. **增加 mask 显示后到 maximize 前的帧数**：把 `rAF()` 改成多个 `rAF()`（3-4 帧），确保 GPU 进程确实收到了带遮罩的帧。

4. **mask 隐藏时机延后**：在 `overlayVisible = false` 之前也加 `rAF()` 等待，确保 `flushCompositorFrame` 的结果已经呈现在屏幕上。

---

**总结**：闪屏的本质是"运行在同一个 WebView2 里的遮罩层，在 OS 级窗口 resize 时无法与窗口管理器同步，从而产生多个时间窗口的内容泄漏"。现有方案解决的是"鼠标移入后脏帧"问题，但 resize 动画期间和遮罩显示/隐藏的时序竞态仍然存在。
